# 操作端（app/ui）人性化设计审查 v2 — 能力缺口推导

> 方法：借用 `ui-design-zh`（UI/UX 设计顾问，已装于 `~/.workbuddy/skills/`）的评审视角——
> **不做现状盘点，做缺口推导**：从"使用者的真实任务"出发，问"完成这件事需要什么"，
> 再对照当前实现，得出**缺失的能力**。
>
> 与 v1（`app-ux-review.md`）的区别：v1 说的是"现有东西哪里不好"，本文说的是"**缺什么**"。

---

## 一、方法：用使用者的任务反推能力

把使用者要做的事拆成 6 个任务链，逐环看"这一步需要界面提供什么"：

| 使用者的任务 | 需要的界面能力 | 当前有吗 |
|---|---|---|
| 1. 知道这东西能干什么 | 能力可发现、可理解 | **部分** |
| 2. 第一次把它配起来 | 有引导、可回退、有验证 | **无（单点卡片）** |
| 3. 让它做事并盯住过程 | 进度可见、可干预、可叫停 | **部分** |
| 4. 出问题时知道怎么办 | 错误可理解、有出路 | **弱** |
| 5. 想改一件已发生的事 | 可撤销、可回看、可对比 | **强** |
| 6. 想确认它没乱来 | 决策可追溯、可复核 | **强** |

**结论先行**：任务 5、6 是这个操作端的**长处**（回执可逆、审计可查、治理透明，
做得比绝大多数同类工具好）。真正的缺口集中在 **任务 1、2、4**——也就是
"**第一次接触**"和"**出事的时候**"这两段。

---

## 二、缺口清单：需要什么

### 缺口 A · 缺少「能力地图」——使用者不知道边界在哪

**现状**：「关于」页有四张卡（它是什么 / 现在能做什么 / 有意不做 / 运行证据），内容其实不错。
但它是**唯一入口**，且是静态长文，且藏在"高级监控"分组里。

**使用者实际会问的问题，界面答不上来**：
- "我能让它帮我做 X 吗？"——没有一个地方能按"我想做的事"来查
- "它现在有哪些工具可以用？"——`/skills` 命令里有，但那是给会用命令的人
- "为什么这个能力时有时无？"——例如任务页三个 tab 默认隐藏，使用者不知为何

**需要的设计能力**：
1. **按意图组织的能力清单**（不是按功能模块）。如"改代码 / 查资料 / 跑命令 / 定时做某事"
   ——每条写清"能做什么、有什么风险、需要我批准吗"
2. **不可用能力要显式说明原因**。例如监视功能没出现时，应该有一行
   "值守监视：需要先设置监视路径" 而不是整个 tab 消失
3. **首次进入时主动展示一次**（现在 `tour-card` 是 `hidden`，要触发才出现）

---

### 缺口 B · 缺少「真正的首次引导」——现在是一张卡片，不是一条路径

**现状**：无模型时 `#setup-card` 出现，要求：选提供方 → 填 Key → 保存 → 测试 → 拉模型。
看起来够用，但**这是单点卡片，不是可回退的路径**：

- **没有步骤感**：使用者不知道"我还要做几步才能开始用"
- **没有回退**：选错提供方、填错 Key，只能重来，无法回到上一步
- **没有完成判定**：保存了 Key 就算成功吗？还是要能发出一条消息才算？
- **没有"我卡住了"出路**：没有本地模型 / 没有 API Key 的人，到这里就走不下去，
  界面也没告诉他"其实可以不配模型，只用文件管理功能"

**需要的设计能力**：
1. **分步向导 + 进度指示**（1/3 实例 → 2/3 引擎 → 3/3 模型）
2. **每步可跳过、可回退、可重入**（中途关窗不留下半配置态）
3. **明确的完成标准**：以"成功发出一轮对话"为终点，而不是"Key 已保存"
4. **失败时给替代路径**：连不上就提示"改用本地端点"或"先跳过，稍后再配"

> 注：`app/UI-BACKLOG.md` 里 R8 的「C12 provisioning 向导」正是这块，
> 状态是**未做**。它是唯一明确的待办。

---

### 缺口 C · 缺少「错误分诊」——出错时只有原文，没有出路

**现状**：错误提示格式普遍是 `动作失败：${r.error}`。抽样：

```
切换失败：${rr.error}      恢复失败：${rr.error}
发送失败：${r.error}       写入被拒：${r.error}
删除被拒：${dr.error}      停止失败：${cr.error}
```

**问题不在文案差，在于只有"复述"没有"分诊"**。使用者看到失败后要能回答三个问题：
1. **是我的问题还是系统的问题？**
2. **我能做什么？**（重试 / 改配置 / 就这样接受）
3. **要不要保留现场？**（复制错误详情去求助）

**需要的设计能力**：
1. **错误分级**：可重试（网络抖动）／需配置（缺 Key）／需决策（权限不够）／需上报（内部错误）
2. **每级给对应动作按钮**，而不是让使用者自己想办法
3. **"复制详情"入口**——现在批准卡有详情展开，但普通错误没有
4. **错误历史**：出错后关掉提示就再也找不到了（toast 4.2 秒消失）

---

### 缺口 D · 缺少「长期状态的一览」——状态散落在多处

**现状**：状态信息分散在：侧栏底部（连接状态）、顶栏 chip（引擎）、composer 下方
statusline（模型/模式/目录/成本）、设置页（版本是否落后）。

**使用者想知道"现在整体什么情况"，需要扫四个地方。**

**需要的设计能力**：
1. **一个可展开的状态总览**（点侧栏底部状态点展开），把"引擎 / 模型 / 目录 /
   是否有任务在跑 / 版本是否落后"聚在一处
2. **异常项优先显示**：例如"版本落后"现在只在设置页的一个 div 里，
   使用者不翻设置页就永远不知道自己在跑旧代码

---

### 缺口 E · 缺少「危险操作的分级反馈」

**现状**：所有确认的**视觉权重相同**。但实际上：

| 操作 | 实际后果 | 当前提示强度 |
|---|---|---|
| 改工作目录 | **重启引擎、中断一切** | 普通说明文字 |
| 删会话 | 不可逆（但已归档可恢复） | 普通确认框 |
| 清空预算 | 影响运行，可改回 | 普通保存 |
| 切换引擎 | 七相交接、可能失败 | 只在一个 chip 上 |

**需要的设计能力**：按后果分级——**会中断运行的**和**可逆的**不该长得一样。
具体：会产生中断的操作，用警示色 + 明确写出"正在运行的任务会被中断"。

---

### 缺口 F · 缺少「空态的行动指引」的一致性

**现状**：空状态文案质量参差。好的：`没有可用模型——去设置里配密钥`。
差的：`没有任务包`、`没有计划`、`没有输出）`（注意那个多余的右括号）。

**需要的设计能力**：统一模板 —— **「这里本该有什么」+「怎么让它出现」+「去哪做」**。
`没有任务包` 应改为 `还没有任务包（.pai/recipes/）——让 AI 用 recipe_save 固化一套步骤，或手动放一个文件进来`。

## 三、做得好的地方（缺口不多，不是客套）

这三块**比大多数同类产品做得好**，是资产而不是待改项：

1. **可逆性（任务 5）**——每次文件写入都留回执，可看差异、可一键回滚，
   且明确区分"回退文件"与"回退时间线"（`已回退——之后的回合仍在文件里，未删除`）。
   这个区分很多人做不对。
2. **治理透明（任务 6）**——批准卡四档分级、载荷超长主动撤掉"总是允许"、
   密钥遮蔽明说、顾问建议标注为参考且不能翻转判定。这些体现了对"人要为自己的批准负责"的尊重。
3. **治理预演**——能在不产生副作用的前提下试跑判定链。这个功能**理念上很好**（虽然入口和输入方式见缺口 E 提到的可用性问题）。

## 四、优先级建议

| 序 | 缺口 | 为什么优先 |
|---|---|---|
| 1 | **B 首次引导** | 唯一有明确待办（C12）的缺口；不做的话新使用者到不了"能用" |
| 2 | **E 危险操作分级** | 代价最低（改文案 + 加确认），收益直接（避免误操作中断任务） |
| 3 | **A 能力地图** | 解决"不知道能干什么"，是把功能用起来的前提 |
| 4 | **C 错误分诊** | 工程量大，但决定了使用者遇到问题是自己解决还是放弃 |
| 5 | **D 状态总览** | 锦上添花 |
| 6 | **F 空态一致性** | 零散修补，可随手做 |

## 五、工具选型（本次查阅 marketplace 后的结论）

| 工具 | 用途 | 适用场景 | 集成方式 | 结论 |
|---|---|---|---|---|
| **`ui-design-zh`**（已装） | UI/UX 设计评审方法论：按使用者任务反推缺口 | 界面评审、交互合理性判断 | 已装 `~/.workbuddy/skills/ui-design-zh/`，纯 prompt 无脚本 | **本次已用**，安全（仅 `read` 工具） |
| `accessibility-audit` | WCAG 2.2 无障碍审计清单 | 需要合规级无障碍检查时 | `npx`/skill 安装 | 暂不需要——axe 已覆盖自动化部分 |
| `z-usability-test-plan` | 生成可用性测试方案模板 | **有真实用户可测时** | 安装后按模板出方案 | 建议后续：目前测试的是自己，价值有限 |
| `user-test-toolkit` | 无侵入采集真实用户操作轨迹 + 微问卷 | **有真实用户使用后** | 需嵌入页面 | **本阶段不适用**——操作端目前是单用户自用 |
| `design-generator` | 从源码/截图产出 DESIGN.md 设计系统包 | 需要建立设计规范时 | 安装后运行 | 可选——若要把现有视觉固化成规范 |

**诚实说明**：marketplace 里**没有**专门的"启发式评估（Nielsen 十原则）"或
"认知走查"类 skill。`ui-design-zh` 是能找到的最贴近的一个，但它给的是**通用评审视角**
（"从使用者角度找问题"），**不含具体检查清单**。所以下表的检查维度是我自己补的：

| 检查维度 | 来源 |
|---|---|
| 能力可发现性 | 补充 |
| 首次引导完整性 | 补充 |
| 错误分诊（可理解/有出路/可保留） | 补充 |
| 危险操作分级 | 补充 |
| 状态可见性 | 补充 |
| 空态行动指引 | 补充 |

## 六、一句话结论

**这个操作端不缺功能，缺的是「第一次接触」和「出事时」这两段的界面能力。**

- 会用它的人（已经配好、熟悉命令）会觉得很好用——回执、审计、治理都到位
- **不会用它的人到不了"会用它"那一步**——没有引导路径、能力边界不明、出错没出路

最该做的三件事：**补完 C12 引导向导（唯一明确待办）、给危险操作分级确认、建能力地图**。
