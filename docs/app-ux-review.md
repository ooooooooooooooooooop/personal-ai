# 操作端（app/ui）人性化设计审查

审查对象：`app/ui/index.html`（547 行）、`app/ui/app.js`（203KB）、`app/ui/style.css`
视角：**站在使用者角度判断"顺不顺手、看得懂看不懂、会不会卡住"**
不涉及：代码质量、测试覆盖、lint、性能指标

---

## 总评

**文案水平明显高于同类工具**，是这套界面的最大资产。空状态几乎逐条都写了"下一步该做什么"：

- `暂无记忆——模型经 memory_save 沉淀，或点上方添加`
- `没有可用模型——去设置里配密钥`
- `暂无档案——/profile save 名字 保存当前 模型/思考档/模式`
- `暂无值守监视——盯住一个路径，变化时自动执行指令`

批准卡的设计也超出一般水平：`允许一次 / 本会话允许 / 总是允许 / 拒绝` 四档分级合理；
载荷超长时**主动撤掉"总是允许"**（因为持久授权不能建立在被截断的载荷上）并明说
`批准/拒绝作用于完整参数`；密钥被遮蔽时也明说。这些都是想清楚了的。

**但存在一类系统性问题：给使用者的「说法」和底层「机制」之间，缺一层翻译。**
下面的问题基本都源于此。

---

## 一、必须修（会让使用者卡住或误解）

### 1. 「AI 引擎」这个入口，使用者不会知道该不该点

侧栏「高级监控 → AI 引擎」，title 是"管理底层执行引擎（Pi / DSH 等）"。
页面内标题「AI 执行引擎」，副标题"查看与管理驱动本系统的底层 Agent 引擎（Pi / DSH 等）"。

**问题**：对绝大多数使用者，"Pi / DSH" 是没有意义的内部代号。这个入口出现在
"高级监控"里，但它的实际操作是**切身体**——而切身体会触发七相交接、可能失败、
可能中断当前任务。这是一个**高影响操作**，却被放在一个听起来无害的"监控"分组里。

**建议**：
- 侧栏项改名为「切换执行引擎」，归入"设置"而不是"高级监控"
- 页面首行加一句人话说明：**"切换引擎会在后台完成交接，当前对话内容会带过去；
  交接期间暂时不能发消息。"**
- 每个引擎卡片上直接标出**能力差异**（当前只有 ≥2 个引擎时才有对照表），
  让使用者知道"换成它我会失去什么"

### 2. 「身体」这个词不该出现在使用者面前

代码与部分文案里用"身体"（body）表示执行引擎——这是架构术语。
`body-chip` 的 aria-label 是"当前 AI 引擎"（已翻译，好），但其它地方仍有裸露风险。

**建议**：全量搜一遍使用者可见文案，把"身体/body"统一成"引擎"或"执行引擎"。
架构文档里叫什么不影响，界面上不能叫。

### 3. 空态首页的三个"起步问题"有误导性

```
浏览项目，告诉我这是做什么的
运行项目测试并修复报错
帮我规划下一步的改动方案
```

**问题**：
- 第二个按钮**会真的跑测试并尝试修改文件**，但它和另外两个并排，看起来像是"随便点点看"
  的示例问题。使用者可能只是好奇点一下，回来发现代码被改了。
- 第三个"帮我规划下一步的改动方案"——"下一步改动"指什么？使用者刚打开应用，
  还没有任何上下文。

**建议**：
- 会动文件的起步问题，在按钮上加一个**轻量标记**（如右侧小字"会改动文件"），
  或改成明确无副作用的措辞（"读一遍测试代码，告诉我哪里有隐患"）
- 第三个改成有明确指向的：「先看看我现在的项目结构，给我一个改进建议」

### 4. 「切换工作目录」的后果说得太轻

设置页原文：`身体在此目录里读写文件。修改会重启当前身体。`

**问题**：**"重启当前身体"会中断正在进行的一切**——正在跑的任务、正在等批准的操作。
但这句话以同样字号埋在一段普通说明里，和"审计保存位置"那类无害信息视觉权重相同。

**建议**：改成警示级表述，并在**有任务在跑时弹确认**：
> ⚠️ 切换工作目录会重启执行引擎，正在运行的任务会被中断。
> [取消] [仍然切换]

### 5. 「预算上限」的三个输入框，使用者不知道填什么

```
本会话 token 上限      如 200000
本会话成本上限（USD）  如 5
本会话调用上限         如 200
```

**问题**：`token` 和"调用"对普通使用者是天书。填多少算正常？填 0 还是留空？
原文说"留空 = 该项不设限"，但没说"填了以后超了会怎样"——
实际会**中止运行**（另处有 `预算超限，运行已中止`），这个关键后果没在这页说。

**建议**：
- 每个输入框加一行说明：token ≈ "模型处理的文字量"，调用 ≈ "工具执行次数"
- 补一句后果：**"达到上限会中止当前会话的运行，需要你手动恢复。"**
- 给一个参考值（如"日常使用约 5–20 万，视任务而定"）

## 二、应该改（影响理解效率）

### 6. 「高级监控」这个名字与内容不符

里面装的是：后台任务、AI 引擎、安全日志、关于。
其中**"AI 引擎"是设置项，"关于"是说明页**——都不是监控。

**建议**：拆开。真正属于"监控"的是后台任务 + 安全日志（保留在此分组）；
AI 引擎归设置，关于移到侧栏底部（与版本号同区）。

### 7. 五个 tab 里三个默认隐藏，使用者发现不了

任务页的 `长期目标 / 协作信箱 / 值守监视` 三个 tab 是 `hidden` + `display:none`，
需要特定条件才出现。

**问题**：条件不满足时，使用者完全不知道系统**有这些能力**——
而「关于」页却在大段宣传 mailbox / durable 调度。**能力宣传与入口可见性矛盾**。

**建议**：要么始终显示（空态给说明），要么在「关于」页对应条目上直接给入口链接。

### 8. 「治理预演」是个好功能，但藏得太深且要求过高

原文：`治理预演：走一遍真实判定链…看这个调用会被放行、拒绝还是询问。`
输入要求：`工具名，如 bash / write / edit` + `参数 JSON（可空）`。

**问题**：要求使用者**手写 JSON**。会写 JSON 的人不需要这个功能，
需要这个功能的人不会写 JSON。

**建议**：做成**从真实历史里选**——列出最近几次被拦截/询问的调用，点一下就预演；
手写输入作为高级选项保留。

### 9. 审批卡缺少"这次批准会持续多久"的时间感

四档按钮文字是 `允许一次 / 本会话允许 / 总是允许 / 拒绝`。

**问题**：`总是允许` 的"总是"到底是**永久**还是**重启后失效**？没说。
这是一个**持久授权**，使用者有权知道它的生命周期。

**建议**：
- 按钮加 title 说明：`总是允许——写入持久白名单，重启后仍生效`
- 「本会话允许」→ 也可以更直白：`这个对话里都允许`

### 10. 错误提示普遍是"失败 + 原始错误串"

抽样：
```
切换失败：${rr.error}
恢复失败：${rr.error}
发送失败：${r.error}
写入被拒：${r.error}
```

**问题**：`r.error` 是后端原文，可能是英文技术信息。使用者看到
"失败：EPERM: operation not permitted" 不知道该干什么。

**建议**：常见错误给一句人话 + 下一步。
如 `发送失败：桥连接失败` 已经不错（有翻译），把它作为标准而不是例外。

## 三、可以更好（打磨项）

| # | 现状 | 建议 |
|---|---|---|
| 11 | 侧栏底部 `v0.1.0` 是裸版本号 | 旁边加"检查更新"或至少 title 说明当前是否落后（`version-stale` 已有逻辑，但提示只在设置页） |

| 13 | 起步问题只有 3 个，且都偏"工程向" | 补一个纯对话向的（如"帮我写一段周报"），让使用者知道这不只是代码工具 |
| 14 | 「命令清单」页有两个大 JSON 文本框 | 对不使用 `.pai/commands.json` 的人是纯噪音。建议默认折叠，标注"进阶" |

## 四、做得好的地方（应保持）

1. **批准卡的载荷透明**：明确区分"截断"与"遮蔽"两种情况，且解释为什么撤掉"总是允许"
2. **空状态几乎全部带下一步指引**，不是干巴巴的"暂无数据"
3. **安全术语翻译到位**：`安全日志`、`凭据过滤`、`治理姿态`——把 `governance` 译成了人能懂的话
4. **「关于」页的"有意不做"** 单独列出并说明是边界不是缺漏，减少使用者误以为"少功能"
5. **风险分级可视化**：`风险·destructive：rm -rf ...` 把判定依据（哪个 class、哪些 unit）直接摊开
6. **顾问建议明确标注为"参考"**且说明不能翻转判定，没有伪装成系统决定

---

## 五、一句话结论

这套操作端的**文字功底和透明性是它的长处**，真正的短板是：
**架构概念（身体、token、治理链）直接透到了使用者面前，中间缺一层"人话翻译"。**

修法不是加功能，是**在已有功能上补说明、改措辞、调入口位置**。
优先级：第 1、2、4、5 条（会卡住或误导）> 第 3、7、8 条（发现不了）> 其余打磨。
