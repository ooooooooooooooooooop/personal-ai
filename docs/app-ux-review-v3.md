## 一、审查总纲

三条原则对应三类问题：

| 原则 | 问什么 | 命中 |
|---|---|---|
| 1 界面只承载 AI 替代不了的东西 | 这个界面元素，AI 能不能答？能答就不该做成功能 | 3 处 |
| 2 按「AI 能否代劳」排序 | 越不可代劳的排越前 | 4 处（含 1 处结构级） |
| 3 能靠设计自明的，不写文字说明 | 这行字，能不能靠视觉/结构省掉？ | 3 处 |

## 二、原则 2 命中（最重的在这）

### ★ P0-1 最不可代劳的两件事，被折叠在默认收起的分组里

**现状**（`index.html` 32–63 行）：

```
工作区
├─ 文件变更与产物      ← 默认可见
└─ 系统设置            ← 默认可见
高级监控  ▸ (details，默认折叠)
   ├─ 后台任务         ← 「正在跑什么」
   ├─ AI 引擎
   └─ 安全日志         ← 「谁批准了什么」
```

**判据**：原则 2 说，排序看"AI 能否代劳"，不是看重不重要。

- `后台任务` = "看清正在发生什么"。AI **不能**替你决定要不要介入——它自己就在跑，你问它"我该不该管"它当然说不用管。**不可代劳。**
- `安全日志` = "谁批准了什么"。这是**追责链条**。AI 不能替你担责。**不可代劳。**
- 对比 `系统设置` 里的主题外观、`文件变更与产物` 的产物列表——这些 AI 完全可以按需回答或代劳。

**结论**：把最不可代劳的两个功能，折进一个默认收起的 `<details>` 里；把可代劳的放在外面。**优先级排序反了。**

**而且折叠本身是坏的**：`side-advanced-group`、`side-advanced-toggle`、`side-adv-arrow`、`side-advanced-items`、`side-section-title` 五个类在 `style.css` 里**零定义**（已逐个 grep 确认，计数均为 0）。这块靠浏览器默认渲染——默认小三角、默认缩进，和整体设计语言脱节，且 `<details>` 原生就是**折叠**状态。

**改法**（不新增页面，只调顺序和层级）：

```
工作区
├─ 后台任务            ← 提到最前，且运行时要有可见活动指示
├─ 安全日志
└─ 文件变更与产物
（AI 引擎留在原地或收进设置——它确实低频）
（去掉「高级监控」这层容器，去掉「工作区」这个分类标题——
 五个项不需要分组，分组是"为了分类而分类"，
 正是 IA skill「常见错误」里的「空层级」）
```

并补上缺失的样式定义。

### P1-2 「中止」按钮只在运行时出现，且藏在输入框右下角

`#abort` 是 `class="send-btn stop hidden"`——隐藏状态切换。位置在 composer 工具栏最右。

**判据**：原则 2 + 例外 B。中断正在运行的任务，**不可代劳**（AI 不能自己决定停自己），且**来不及**（事后再问就晚了）。

现在的做法是"运行时才显形"——但用户**在它出现前的那一刻**最需要知道"我能不能停"。而且它和 `插话`、`用量`、`模式`、`模型` 挤在同一行，视觉权重和"换个模型"一样。

**改法**：运行中时，把「中止」从工具栏里提出来，成为输入框区域**独立且视觉醒目**的控件（不靠文字标签，靠位置+面积+色彩自明）。这直接呼应例外 B 的"靠视觉而非文字"。

### P1-3 授权卡片按钮数随载荷变化，用户无法形成稳定预期

`app.js` 655–720 行：ASK 卡片固定四个按钮（允许一次 / 本会话允许 / 总是允许 / 拒绝），但**载荷被截断时移除"总是允许"**。

**判据**：原则 2——批准/拒绝是"最高"优先级，必须由人承担。既然如此，它的**选项集合不该随技术细节变**。用户上次看到四个，这次看到三个，会以为是 bug 或以为"总是允许"被我弄丢了。

**改法**：保四个按钮不变，把"总是允许"置灰并在**原位**给出原因（如"内容已截断，本次不能总是允许"）。截断是技术状态，不该改变法律性选项的数量。

### P2-4 「清理历史」「全部停止」是文本按钮，风险不对等

`#jobs-clear-history`（清空历史，可逆性差）和 `#jobs-stop-all`（终止所有任务，不可逆）都用 `class="btn ghost sm"`，**同一视觉权重**，且都靠 `title` 属性解释。

违反例外 B（危险操作须靠视觉识别）和原则 3（不靠文字）。

**改法**：`全部停止` 应视觉升级（这是会打断运行的操作）；`清理历史` 降级。至少两者不能长得一样。

## 三、原则 1 命中

### P1-5 空状态的三条起步示例，是"引导"

`#starters` 三条：浏览项目 / 运行测试 / 规划改动。

**判据**：原则 1 明确列出"上手引导、教程"不做成界面功能——**人会直接问 AI**。

**但要注意分寸**：这不是要删掉整个空状态。用户自己已说过"引导不重要甚至能够删除"。空状态需要的只是一个**视觉锚点**告诉人"这里可以打字"（`输入框就在下面`），而不是三条**预设指令**。预设指令还隐含一个错误暗示：这个应用只会干这三件事。

**改法**：删 `#starters` 三条按钮，保留 `mascot` + 标题。或最多留一条、并且是**当前上下文相关**的动态建议（不是三条静态的）。

### P1-6 「高级监控」这个命名本身是给专家的，且用文字解释了它的内容

`<summary title="展开底层系统诊断与高级监控">高级监控</summary>`——用 `title` 文字说明这里是什么。

**判据**：原则 1（AI 能解释的东西不写成界面文字）+ 原则 3。用户不需要界面告诉他"这里是高级监控"，他需要一眼看到里面有他要的东西。

**改法**：随 P0-1 一起，去掉这层容器。内容直接平铺。

### P2-7 `#tour-card` 的存在

`index.html` 里有 `#tour-card.hidden`。既然用户说引导可删、原则 1 也否掉引导——**先确认它是否还活着**。若是死代码，删；若仍会触发，按原则 1 删功能。

## 四、原则 3 命中

### P1-8 大量 `title` 属性在承担"说明"职责

侧栏每个 `nav-item` 都带 `title`：

- `title="查看 AI 产生的文件变更回执与导出产物"`
- `title="配置模型密钥、工作目录与偏好"`
- `title="查看后台正在运行的长程自动化任务与计划作业"`
- `title="管理底层执行引擎（Pi / DSH 等）"`
- `title="查看安全规则判定、凭据过滤与 Token 消耗审计"`

**判据**：原则 3。这些文字在解释**图标+标签本来该自明的东西**。如果一个图标需要一句话解释，那是图标选错了。

另外 `title` 在触屏上根本不可达——写了等于没写。

**改法**：要么换自明的图标，要么认了"这个入口就是需要从别处被发现"，而不是用悬停文字兜底。

### P1-9 输入框 `placeholder` 过长承担说明职责

`placeholder="输入需求或问题…"` 尚可；但 `#mon-prompt` 的 `placeholder="触发时执行的指令，如：总结这个目录的变更"` 是**在 placeholder 里写教程**。

违反原则 3。placeholder 不是文档位。

### P2-10 设置页八张卡片平铺，无分层

`view-settings` 有 8 张卡片 + `.set-nav-pills` 导航。主题外观类设置与密钥、工作目录类设置**同一呈现层级**——虽然 pills 有分组，但默认视图没有按"AI 能否代劳"给出视觉轻重。

呼应原则 2：纯偏好类（主题、外观）应**最不显眼**。

## 五、两条例外的核查

例外 A/B 是原则 1 的边界——这两种情况界面**必须**自己说清。核查结论：

### 例外 A（AI 不在循环里）——**基本达标，一处需补**

已做的：`#setup-card` 在未配密钥时接管空状态，给出 provider 选择 + 密钥输入 + 测试连接。这是对的——此刻问不了 AI，界面必须自己带路。

`#status-dot` + `#status`（"连接中…"）也在侧栏底部承担桥状态。

**需要补的**：桥断/引擎崩时，聊天区是否给出**出路**（不只是"连接失败"）。要在代码里核实 `statusline` 与 `#status` 的分工。

### 例外 B（危险操作）——**不达标**

直接对应 P2-4 和 P1-2：

- `全部停止` 与 `清理历史` 视觉同权 ✗
- `中止` 藏在工具栏 ✗
- 授权卡片选项会变 ✗

例外 B 是**必须靠视觉而非文字**——当前三处都依赖文字（`title` / 标签 / 位置暗示）。

## 八、已核实的两处事实（读码确认，非推测）

### 8.1 `#tour-card` 是死代码 —— 确认

`grep -n 'tour' app.js` → **零命中**。`index.html` 里残留 `<div id="tour-card" class="hidden">`，但没有任何代码会移除它的 `hidden`。

**处理**：直接删 HTML 残骸。不需要按原则 1 讨论"该不该有引导"——它本来就没在跑。

### 8.2 例外 A（AI 不在循环里）—— **不达标，且比预想严重**

桥断路径（`app.js:4223`）：

```js
setStatus('连接断开，重试中…', 'err');
```

**只有状态，没有出路。** 没有说重试多久、没有给手动重连入口、没有说此刻输入的东西会不会丢。

而这是例外 A 的核心要求——"AI 不在循环里时，界面必须自己把状态**和出路**说清"。现在只有前半句。

**更严重的一条**（`app.js:1291`）：

```js
setStatus(`身体崩溃，${Math.round((ev.inMs ?? 1000) / 1000)}s 后自动重启（第 ${ev.attempt} 次）…`, 'err');
```

身体（执行引擎）正在崩溃重启——这是**最需要人知道**的时刻之一。而它：

1. 只出现在**侧栏底部的小字**（`.side-foot`），用户可能在聊天区完全没看见；
2. 紧接着 `app.js:1293` `setStatus('就绪')` 会**立即把它覆盖掉**；
3. 没有对应到 `后台任务`（AI 引擎）页面的身体状态卡片。

**这正好印证 P0-1**：身体崩溃的信息，流向了最不显眼的地方；而它本该在"AI 引擎"入口的可见状态上体现，甚至该在运行中时于聊天区顶部显示。

### 8.3 `#statusline` 与 `#status` 的分工 —— 确认分裂

- `#statusline`（`app.js:2952`，注释写明 "model, mode, ..."）——**常驻底部行**，展示模型/模式等**持续状态**。
- `#status` + `#status-dot`（`app.js:2991` `setStatus()`）——**瞬时事件**（重试/崩溃/断开）。

问题：**瞬时事件的容器是个会被覆盖的文本框**。`setStatus` 写入即覆盖，崩溃信息写进去、下一句话就抹掉了。瞬时事件需要的是**可追溯的存在**（留痕 / 可展开），而 `setStatus` 是个覆盖式状态位——**语义不匹配**。
