## 1. Positioning & design philosophy

OpenCode bets on **the harness as a platform server**. Where most harnesses are terminal applications with an agent core, OpenCode is architected as a local HTTP/WebSocket server (typed Effect `HttpApi`) that any client — its own TUI, a desktop app, a web app, an ACP-driven IDE, third-party SDK consumers — attaches to. The second bet is **provider breadth as a first-class subsystem**: a curated model catalog (models.dev data), a static map of ~20 Vercel AI SDK provider packages, plugin-defined providers with their own auth flows, and a per-model prompt/tool surface. Compared with Pi's "minimal core + extensions" and Vibe's "opinionated profiles," OpenCode's center of gravity is *surface area*: the message log is the work queue, sessions are rows in SQLite, permissions are a layered rule language, and almost every subsystem is reachable through the API. [INFERENCE — drawn from server/plugin/provider structure]

## 2. Architecture overview

- **Monorepo** (Bun workspaces + Turbo): the product lives in `packages/opencode`; shared lower layers are split into `packages/core` (Effect services, Drizzle/SQLite database, models-dev catalog, V2 session core), `packages/schema` (wire/domain schemas), `packages/llm` (native LLM transport + `LLMClient`/`RequestExecutor`), `packages/plugin` (plugin SDK types), `packages/sdk`/`sdk-next`/`client`, `packages/tui`, `packages/app`, `packages/desktop`, `packages/web`. (src: `packages/`, `package.json` workspaces @ e03db9bc)
- **Service architecture**: everything is an Effect service built as `LayerNode`s and scoped per open directory via `InstanceState` (a `ScopedCache` keyed by project directory — two open projects get isolated service instances). (src: `packages/opencode/src/effect/instance-state.ts`, per-file `node = LayerNode.make({...})` tails @ e03db9bc)
- **Two session runtimes coexist**: the shipping loop is the "V1" path in `packages/opencode/src/session/` (`prompt.ts`, `processor.ts`, `compaction.ts`); a redesigned "V2" core exists in `packages/core/src/session/` with a durable `session_input` inbox, `SessionRunner`, `SessionRunCoordinator`, and event-sourced projections — the root AGENTS.md documents V2 invariants ("Keep durable prompt admission separate from model execution…"), indicating an in-flight migration. (src: `packages/opencode/src/session/prompt.ts`, `packages/core/src/session/`, `AGENTS.md` "V2 Session Core" @ e03db9bc)
- **Entry points**: `bun run src/index.ts` → CLI/TUI, server (`server/server.ts` — `HttpApiApp` + `HttpRouter.serve` + WebSocket tracker + mDNS), `acp/` adapter, SDK packages. [FACT]

## 3. Agent loop

- **Shape**: `SessionPrompt.runLoop` is a literal `while (true)` that re-reads the persisted message list each iteration (`MessageV2.filterCompactedEffect`), derives `{ user, assistant, finished, tasks }` via `MessageV2.latest`, and exits when the last assistant message has a terminal finish reason and no un-executed tool parts. The paper's "log-as-queue" characterization is accurate: **`tasks` are `compaction` and `subtask` message *parts* persisted in the log itself** — the loop pops a task part and dispatches to `handleSubtask` or `compaction.process`, so pending work survives restarts. (src: `packages/opencode/src/session/prompt.ts:1081-1160`, `message-v2.ts:592-597`, `packages/schema/src/v1/session.ts` `SubtaskPart`/`CompactionPart` @ e03db9bc)
- **Step cap**: `agent.steps ?? Infinity`; when `step >= maxSteps` the loop appends an assistant message containing `MAX_STEPS_PROMPT` ("you are about to hit your step limit…") rather than aborting — a nudge, not a kill-switch. (src: `session/prompt.ts:1178-1179,1281`, `packages/core/src/session/runner/max-steps.ts` @ e03db9bc)
- **Turn processing**: each step creates a `SessionProcessor` handle that streams `llm.stream(input)` as an `LLMEvent` stream; every event (reasoning-*/text-*/tool-*/step-*/finish) is persisted to SQLite as message parts as it arrives (`session.updatePart`/`updatePartDelta`). Tool parts move pending→running→completed|error; the Vercel AI SDK executes tool `execute()` callbacks inside the stream, so tools within one step run concurrently with no harness-level cap. (src: `session/processor.ts:278-550`, `session/tools.ts` @ e03db9bc) [FACT]
- **Retry**: `SessionRetry.policy` — 2s initial delay ×2 exponential +25% jitter, max 5 retries; honors `retry-after-ms` and `retry-after` (seconds or HTTP-date) headers with a 30s cap when no headers; a large regex battery classifies retryable provider/network/5xx errors; `ContextOverflowError` is explicitly non-retryable and instead sets `needsCompaction`, which truncates the stream (`Stream.takeUntil`) and routes the next loop iteration into compaction. (src: `session/retry.ts:26-207`, `processor.ts:613-697` @ e03db9bc)
- **Loop guards**: `DOOM_LOOP_THRESHOLD = 3` — three consecutive tool calls with identical name+input trigger a `doom_loop` permission ask; `experimental.continue_loop_on_deny` controls whether a rejected tool ends the loop; `content-filter` finish reasons surface as errors. No cost guard or planner. (src: `processor.ts:29,356-380,647`, `prompt.ts:1295-1317` @ e03db9bc)

## 4. Tool system

- **Inventory** (`tool/registry.ts`): `invalid` (schema-error feedback), `question`, `shell` (named `bash`/`powershell` per platform), `read`, `glob`, `grep`, `edit`, `write`, `task`, `webfetch`, `todowrite`, `websearch`, `skill`, `apply_patch`, plus flag-gated `execute` (experimental code-mode over MCP), `lsp`, `plan`/`plan_exit` (experimental plan mode). `question` is client-gated (app/cli/desktop). [FACT]
- **Model-family tool surface**: `usePatch = modelID.includes("gpt-") && !oss && !gpt-4` — GPT-5-class models get `apply_patch` *instead of* `edit`/`write`; all other models get `edit`+`write`. The tool surface literally co-varies with the model. (src: `tool/registry.ts:297-300` @ e03db9bc)
- **Edit mechanism**: `tool/edit.ts` — exact `oldString`→`newString` replace with a **9-replacer fallback chain** (Simple → LineTrimmed → BlockAnchor (Levenshtein first/last-line anchors) → WhitespaceNormalized → IndentationFlexible → EscapeNormalized → TrimmedBoundary → ContextAware → MultiOccurrence), BOM + original line-ending preservation, per-file semaphore lock, `replaceAll` flag, LSP diagnostics fed back to the model on save. (src: `tool/edit.ts:226-737` @ e03db9bc)
- **Shell**: `tool/shell.ts` parses every command with web-tree-sitter (bash + PowerShell WASM grammars) *before* execution — see §6. Execution is a direct child process on the host shell (`ChildProcess.make(command, [], { shell })`), 2-minute default timeout, output streamed with a rolling 2×maxBytes buffer that spills to a truncation file, response tailed to `MAX_LINES=2000`/`MAX_BYTES=50KB` with `Full output saved to: <path>`; `<shell_metadata>` conveys timeout/abort. (src: `tool/shell.ts:257-625`, `tool/truncate.ts:14-17` @ e03db9bc)
- **MCP tools/resources**: MCP tool calls are wrapped per-tool with `ctx.ask({permission: <mcp_tool_name>})`; servers advertising `resources` capability additionally register three synthetic tools (`list_mcp_resources`, `list_mcp_resource_templates`, `read_mcp_resource`) gated by `read` permission with `mcp:<server>:*` patterns and a 10MB/mime-allowlist blob cap. MCP *prompts* surface as slash commands. (src: `session/tools.ts:27-488`, `mcp/index.ts` @ e03db9bc)
- **Custom tools**: `{tool,tools}/*.{js,ts}` globbed from all config directories + plugin-registered `tool` map; Zod or JSON-Schema args normalized at the registry boundary; plugin `tool.execute.before/after` and `tool.definition` hooks wrap every call. (src: `tool/registry.ts:121-204` @ e03db9bc)

## 5. Context management

- **System prompt** (assembled in `session/llm/request.ts:56-78` + `session/system.ts`): `[model-family prompt] + [environment block] + [instruction files] + [MCP instructions] + [skills]` — an agent's own `prompt` replaces the family prompt. `environment()` emits model id, cwd, workspace root, git-repo flag, platform, date, plus `<available_references>` for configured reference directories. (src: `session/system.ts:28-138` @ e03db9bc)
- **Prompt matrix**: `SystemPrompt.provider(model)` dispatches on `model.api.id` substrings: `muse*`→meta.txt (MODEL_NAME templated), `gpt-4`/`o1`/`o3`→beast.txt, `gpt-6`→gpt-astra.txt, `codex`→codex.txt, `gpt`→gpt.txt, `gemini-`→gemini.txt, `claude`→anthropic.txt, `trinity`→trinity.txt, `kimi`/moonshotai providers→kimi.txt, else default.txt — 10 variants on disk (`session/prompt/*.txt`, plus plan-mode/build-switch/reminder prompts). Matches the paper's "model-family prompt matrix." [FACT]
- **Instruction files**: `session/instruction.ts` — `AGENTS.md`/`CLAUDE.md` from global config dir + first project-level match walking up from cwd (CLAUDE.md gated by `disableClaudeCodePrompt` flag); remote instruction URLs fetched over HTTP; instruction state is cleared per assistant message (`instruction.clear`). [FACT]
- **Compaction** (`session/compaction.ts`): triggered when `isOverflow(lastFinished.tokens)` or a `ContextOverflowError`/`compact` result. Selection keeps a **tail of whole user-turn boundaries** within `compaction.preserve_recent_tokens` (default ≈ 25% of usable context, clamped 2k–15k), with a mid-turn `splitTurn` fallback; `tail_turns` caps turn count. The summarizer is the hidden `compaction` agent run with `tools: {}` — the processor hard-throws on any tool call during a summary turn. Prompt = fixed section template (Objective / Important Details / Work State(Completed·Active·Blocked) / Next Move / Relevant Files) + incremental `<prior-summary>` merge instructions (`packages/core/src/session/compaction.ts:16-55`). On *overflow* compaction it walks back to the previous user message and replays it with media parts degraded to text markers, then auto-continues via a synthetic user message ("Continue if you have next steps…", `metadata.compaction_continue`). Plugin hooks `experimental.session.compacting` (inject/replace prompt) and `experimental.compaction.autocontinue` (veto) wrap the whole flow. [FACT]
- **Pruning**: opt-in `compaction.prune` — after each run, walks parts newest→oldest, protects the newest turn and `skill` outputs, keeps ~40k tokens of tool output, then marks older completed tool parts `state.time.compacted` (rendered to the model as `[Old tool result content cleared]`) — soft-delete pruning distinct from summarization. (src: `session/compaction.ts:271-317` @ e03db9bc)
- **Retrieval**: grep/glob/read/LSP only; no embeddings or vector store anywhere — consistent with the paper's corpus-wide finding. [FACT]

## 6. Safety model

- **Rule language**: permission = `{permission, pattern, action: allow|deny|ask}` triples; evaluation is **last-match-wins** over concatenated rulesets (`findLast` on `rulesets.flat()`, default `ask`). Layer order: built-in defaults → built-in agent rules → user `permission` config → per-agent config → per-session rules (set via prompt input). (src: `permission/index.ts:28-38`, `agent/agent.ts:119-294` @ e03db9bc)
- **Defaults**: `*`: allow; `doom_loop`: ask; `external_directory` `*`: ask with allowlist for the truncation dir, tmp, skill dirs, configured references; `question`/`plan_enter`/`plan_exit`: deny (agent profiles re-allow them); `read` `*.env`/`*.env.*`: ask (but `*.env.example`: allow). Permissive inside the project by default; asks trigger on outside-worktree paths, env files, and loop signatures. [FACT]
- **Approval flow**: `Permission.ask` publishes a `permission.asked` event and suspends on a `Deferred` until `reply` — "once" | "always" (persists the request's `always` patterns into a session-approved list and auto-resolves matching pending asks) | "reject" (optionally with corrective feedback via `CorrectedError`, and cascades to reject *all* pending asks in the session). [FACT]
- **Syntax-aware shell permissions**: the tree-sitter scan extracts every `command` node (including inside substitutions/subshells); file-mutating commands (rm/cp/mv/cat/chmod/…, cmd/PowerShell verbs) have path args resolved and checked against the project boundary → `external_directory` ask with `dir/*` globs; each command's verbatim source becomes the ask pattern and an LLM-generated **arity table** (`permission/arity.ts`: `git`→2 tokens ⇒ `git checkout *`) produces the "always" pattern. Dynamic args (`$`, backticks, `$(…)`) are skipped for path detection — i.e., expansion smuggling is not fully defended (documented as pattern-based, not a sandbox). (src: `tool/shell.ts:257-414`, `permission/arity.ts` @ e03db9bc)
- **Deny ⇒ invisible tool**: `Permission.disabled` maps edit/write/apply_patch→`edit` and MCP-resource tools→`read`; a wildcard `deny` removes the tool from the model-visible surface entirely (`session/llm/request.ts:208-214`, `registry.ts:265-278`). [FACT]
- **No OS sandbox**: shell runs as the invoking user; the safety boundary is permissions+approvals, plus the snapshot system for *audit/rewind* (not isolation). Plan-mode agent denies all edits except `*.md` under plans dirs. Plugin hook `permission.ask` can override any decision. (src: `tool/shell.ts`, `agent/agent.ts:156-181`, `packages/plugin/src/index.ts:261` @ e03db9bc)

## 7. Orchestration

- **Subagents**: `task` tool spawns a **child session** (`parentID` set) — resumable via `task_id`, permission rules derived via `deriveSubagentSessionPermission` plus auto-deny of `todowrite`/`task` unless the subagent config says otherwise; depth limited by `subagent_depth` (default 1, counted by walking `parentID`). Foreground = await child loop result (last text part); background mode (`experimentalBackgroundSubagents` flag) runs via `BackgroundJob` and injects the result into the parent as a synthetic `<task>` text part. (src: `tool/task.ts:92-360` @ e03db9bc)
- **Pending subtasks**: `subtask` parts persisted in the log let the loop pick up queued child work across restarts (`prompt.ts:1144-1147`). [FACT]
- **Agents/modes**: built-ins `build` (default primary), `plan` (read-only primary), `general`+`explore` (subagents), hidden `compaction`/`title`/`summary` agents; `mode` ∈ primary|subagent|all; user-defined agents from config or `{agent,agents}/**/*.md` (frontmatter config + body prompt) and legacy `{mode,modes}/*.md`. (src: `agent/agent.ts:140-265`, `config/agent.ts` @ e03db9bc)
- **Surfaces**: Effect `HttpApi` server (`server/routes/instance/httpapi/groups/`: session, permission, question, provider, mcp, config, event, file, pty, workspace, sync, tui, project, control-plane…) + WebSocket events + mDNS discovery; `acp/` implements the Agent Client Protocol for IDE clients; TUI (`packages/tui`, OpenTUI), desktop app, web app, Slack integration, typed JS SDK (`packages/sdk`, `sdk-next`). Headless `opencode run` exists alongside the server. [FACT]
- **Parallelism**: tool calls inside a step run concurrently; sessions are per-directory `InstanceState`-isolated; background jobs keyed by session ancestry. [FACT]

## 11. Notable mechanisms

1. **Log-as-queue loop** — `compaction`/`subtask` parts persisted in the message stream are the work queue; a `while(true)` re-reads the log each step, so crashes, retries, and drive-by tasks all ride the same structure. (`session/prompt.ts:1081-1160`, `message-v2.ts:592-597`)
2. **Shadow-git snapshots per step** — `step-start`/`step-finish` parts carry `write-tree` hashes into a separate GIT_DIR sharing object storage with the real repo; revert restores files by hash — versioning the *filesystem* inside the transcript. (`snapshot/index.ts`, `processor.ts:424-497`)
3. **Arity-table permission patterns** — an LLM-generated command-arity dictionary turns `git checkout -b foo` into the always-pattern `git checkout *`, making "always allow" mean the *command shape*, not the literal string. (`permission/arity.ts`, `tool/shell.ts:407-410`)
4. **Deny-removes-tool symmetry** — permission `deny` doesn't just block calls; it deletes the tool from the model's schema list, so policy changes the model's action space, not just its outcomes. (`permission/index.ts:204-219`, `session/llm/request.ts:208-214`)
5. **Interrupted-orphan handling** — tool parts abandoned mid-stream are marked `metadata.interrupted`, excluded from the "has pending tool calls" check and from assistant prefill, preventing stuck `tool_use` blocks from wedging the loop after aborts/retries. (`prompt.ts:96-100,1100-1130`, `processor.ts:591-608`)
6. **Compaction-as-agent** — the summarizer is a hidden agent (`*`-deny, own prompt) executed through the same processor with `tools: {}` and a hard tool-call guard; plugin hooks can replace its prompt or veto the auto-continue. (`session/compaction.ts:358-460`, `agent/agent.ts:219-233`)
